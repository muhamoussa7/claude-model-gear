# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Model Gear, a Claude Code mod that picks the model and reasoning effort for each prompt the person types, with a footer chip to toggle it. Slash command: `/modelgear on|off|status`.

This repo is public on GitHub (`muhamoussa7/claude-model-gear`). It is also the only copy of the plugin. The marketplace is `.claude-plugin/marketplace.json` (named `claude-model-gear`), and the plugin lives in `model-gear/`. The older `MODS/model-gear` copy was removed on 2026-10-22, so do not recreate it.

## Commands

There is no build step, no bundler and no installed dependencies. TypeScript is checked and tests are run by the `claude` CLI itself:

```
claude plugin validate model-gear
claude plugin test model-gear
```

These are the commands the bundled type definitions name (`model-gear/.claude-plugin/types/claude-code/index.d.ts`). Tests import from `claude-code/testing`, which only exists under `claude plugin test`, so `node`, `tsc` and `bun test` will not work. To run one test file, check `claude plugin test --help` for a filter option.

## Releases

Bump `version` in `model-gear/.claude-plugin/plugin.json` for every release. Installed copies are cached by version, so an unchanged version can keep the old code in place.

The `model-gear/.claude-plugin/types/` folder is generated by Claude Code and listed in the root `.gitignore`. Keep it in the working copy so tests run, but do not commit it.

## Plugin layout

- `model-gear/.claude-plugin/plugin.json` declares name, version and `"types": "./types/index.d.ts"`.
- `model-gear/.claude-plugin/types/` is generated typings for the `claude-code` host API. Treat it as read-only reference and search it when you need an engine API.
- `model-gear/hooks/hooks.json` lists `./register.tsx` as the one module.
- `model-gear/hooks/register.tsx` exports `register: Register` and wires event hooks with `on(...)`.
- `model-gear/hooks/logic.ts` holds the pure functions (parsing, guessing, label building) so they can be tested without an engine.
- `model-gear/hooks/model-gear.test.ts` tests `logic.ts` directly and exercises `register` through a mock engine.
- `model-gear/types/index.d.ts` defines the plugin's own types and augments `PluginState` in the `claude-code` module. The `atom({ plugin, key })` calls in `register.tsx` must use literals that match that interface.

JSX uses a custom factory (`jsxFactory: "h"`). Components are not imported: `$.ui.resolve(e)` returns `Box`, `Text`, `Button` and `Input` for the current surface.

## Conventions

- Every hook handler wraps its work in `try`/`catch` and falls through to `next(e)`, and each `on(...)` ends in `.catch(...)` that does the same. A failure in the mod must never block the person's prompt.
- State lives in two places. `atom` plus `read`/`update` (`$.state`) drives the UI. `$.store` persists across sessions and reloads. Writers update both, and `session.start` rehydrates the atoms from the store.
- User-facing strings are plain sentences that say what happened and what was left unchanged.
- Flags are named `isX`, matching the typings (`isLocked`, `isEnabled`).

## How it works

The flow on `prompt.submit` (`register.tsx` `pickModel`):

1. Skip unless the prompt was typed while idle (`isTypedWhileIdle`), is not a slash command and is not a short acknowledgement (`isShortReply`).
2. Ask the smallest model in the install's `model` config row for "level effort" in two words (`askSmallModel`, 4s timeout). If it fails, `guessLevel` and `guessEffort` in `logic.ts` fall back to keyword regexes.
3. Effort named in the prompt ("ultrathink", "max effort") overrides the classifier.
4. `candidatesFor` orders model options for the level and `config.set` tries each until one is accepted.

Details that need several files to see:

- Models are matched by line name (`haiku`, `sonnet`, `opus`, `fable`) found inside the option string, so new versions work without code changes. Level to line is the `LEVEL_LINE` table.
- The engine has no effort row in `/config`. Effort is injected per request in the `turn.step` hook (`effortToSend`) for the main loop and its subagents alike. It is never saved in settings. Subagents keep their own model. The effort sent is also written to the store under `effort` for the person's status bar, and deleted when Model Gear turns off. The model and effort of the last prompt are pinned under the prompt with `$.ui.status` (`statusLine`), cleared when off.
- `applied` in the store is the model Model Gear last set. A hand `/model` or `config.set` from the composer turns the plugin off without restoring, and a toast says why. A model that differs on the next prompt without such a call (seen after `/compact`, or from another window sharing the setting) does not turn it off; it sorts the prompt again. A bare `/effort` counts only if the saved effort actually changed, since the menu can be cancelled.
- Turning on saves the current model as `previous`. Turning off through the command or the chip restores it via `restoreValue`.
